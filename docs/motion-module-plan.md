# 运动模块开发规划

## 目标

当前阶段只专注运动模块，先完成一条最小可用闭环：

1. 进入运动页
2. 点击“开始运动”
3. iOS 原生开始连续定位
4. Flutter 实时接收位置、速度、距离、时长
5. 地图显示当前位置和运动轨迹
6. 点击“结束运动”
7. 生成一条完整运动记录

现阶段先不做首页历史汇总、分享、成就等扩展功能，先把运动主链路打通。

## 当前协作约束

- 带删除线的实施步骤表示已完成，后续推进时不再作为待开发项重复实现。
- 当前仓库中的 `MotionPage` 只作为调试页和联调面板，不代表最终运动模块 UI。
- 正式开始运动模块 UI 开发前，必须先通知用户，并等待用户提供 UI 设计图。
- 在拿到 UI 设计图前，开发重点放在正式 UI 之前的准备工作，包括状态管理、交互链路、原生联调、数据协议、事件流和验收整理。
- 当前推荐策略是：先把前期准备工作做完整，再单独进入 UI 开发阶段，避免调试页直接演变成正式页面。
- 用户现已提供 Figma 设计链接，可进入正式 UI 规划与实施文档确认阶段；在文档确认前，仍不直接开始代码实现。

## 技术路线

- 地图和定位：iOS 原生高德 SDK
- 业务界面和状态管理：Flutter
- 状态管理：`flutter_riverpod`
- Flutter 与原生通信：
  - `MethodChannel`：Flutter 下发命令
  - `EventChannel`：原生持续推送运动数据

## 模块职责划分

### Flutter 负责

- 运动页 UI
- 开始、暂停、继续、结束按钮交互
- 运动状态管理
- 实时数据展示
- 运动记录模型
- 后续本地存储和历史展示

### iOS 原生负责

- 高德地图承载与显示
- 高德定位接入
- 定位权限申请
- 连续位置更新
- 轨迹点采集
- 距离与基础统计计算
- 向 Flutter 推送实时数据

## 先定义通信协议

在正式开发前，先统一 Flutter 和原生之间的数据结构，避免后面反复改字段。

### 建议命令接口

`MethodChannel`

- `requestLocationPermission`
- `startWorkout`
- `pauseWorkout`
- `resumeWorkout`
- `stopWorkout`
- `getLocationServiceStatus`

### 建议事件接口

`EventChannel`

- 定位状态变更
- 最新位置点
- 实时运动统计
- 错误事件

## 数据模型建议

### MotionPoint

表示单个轨迹点，建议包含：

- `latitude`
- `longitude`
- `timestamp`
- `speed`
- `accuracy`
- `altitude`（可选）

### MotionRealtime

表示运动中的实时状态，建议包含：

- `distanceMeters`
- `currentSpeedMps`
- `averageSpeedMps`
- `durationSeconds`
- `latestPoint`
- `pointCount`

### MotionSession

表示一次完整运动记录，建议包含：

- `startTime`
- `endTime`
- `durationSeconds`
- `totalDistanceMeters`
- `averageSpeedMps`
- `points`

## 统一数据单位

为了避免 Flutter 和原生换算混乱，建议统一约定：

- 距离：米
- 速度：米/秒
- 时间：毫秒时间戳或秒级时长
- UI 展示层再转换为 `km`、`km/h`

## 分阶段开发步骤

## 第一阶段：定边界

目标：明确 Flutter 与 iOS 原生的职责边界。

产出：

- Flutter 负责的页面与状态范围
- iOS 原生负责的地图与定位范围
- `MethodChannel` / `EventChannel` 通信方式

## 第二阶段：设计运动数据协议

目标：先把数据字段和事件类型定下来。

产出：

- 运动点结构
- 实时数据结构
- 完整运动记录结构
- 原生到 Flutter 的事件格式

## 第三阶段：打通原生最小闭环

目标：先验证原生能力和 Flutter 通信是通的。

具体事项：

1. 接入高德地图 iOS SDK
2. 接入高德定位 iOS SDK
3. 配置 iOS 定位权限
4. 原生地图显示当前位置
5. 连续获取定位点
6. 原生侧采集轨迹并累计基础数据
7. 通过 `EventChannel` 推送到 Flutter

这一阶段重点验证三件事：

- 真机可以稳定定位
- 定位点可以持续返回
- Flutter 可以实时收到事件

## 第四阶段：搭建 Flutter 运动状态机

目标：先让页面逻辑稳定，避免按钮和状态乱掉。

建议状态：

- `idle`
- `preparing`
- `running`
- `paused`
- `finished`
- `error`

建议用 `Riverpod Notifier` 统一管理：

- 当前运动状态
- 当前轨迹点
- 当前距离
- 当前速度
- 平均速度
- 已运动时长
- 错误信息

## 第五阶段：实现运动页最小 UI

目标：先做一个可操作、可观察的页面，不追求最终视觉。

页面建议拆成四块：

1. 顶部状态区
   - GPS 状态
   - 当前运动状态
2. 地图区
   - 承载原生高德地图
3. 实时数据区
   - 当前距离
   - 当前速度
   - 平均速度
   - 已运动时长
4. 底部操作区
   - 开始
   - 暂停/继续
   - 结束

## 第六阶段：补统计与轨迹逻辑

目标：让运动数据从“能跑”变成“能用”。

重点处理：

1. 轨迹点过滤
   - 去掉精度差的点
   - 去掉漂移点
   - 去掉异常跳点
2. 距离累计
   - 不只依赖 SDK 原始值
   - 保留自己的累计逻辑
3. 速度展示
   - 对瞬时速度做平滑处理
4. 暂停逻辑
   - 暂停期间不累计距离和有效运动时长
5. 结束逻辑
   - 生成完整 `MotionSession`

## 第七阶段：保存运动记录

目标：结束运动后能落下一条完整记录，为首页和“我的”做准备。

至少保存：

- 开始时间
- 结束时间
- 总时长
- 总距离
- 平均速度
- 轨迹点集合或简化后的轨迹

存储方案可以后面定，当前阶段先预留接口即可。

## 第八阶段：补权限和异常处理

目标：让模块具备基本产品可用性。

至少覆盖这些场景：

- 用户拒绝定位权限
- 定位服务关闭
- 运动中定位中断
- App 退到后台再回前台
- 高精度定位不可用
- 运动过程中发生原生错误

## 推荐开发顺序

建议按下面顺序推进：

1. 先定 Flutter 与原生通信协议
2. 接入高德地图和定位原生能力
3. 真机验证定位和轨迹事件回传
4. 搭建 Flutter 运动状态机
5. 完成运动页最小 UI
6. 接入实时数据展示
7. 打通开始、暂停、继续、结束闭环
8. 补轨迹过滤、统计计算和记录保存

## 正式 UI 开发阶段（Figma 驱动）

### 阶段目标

基于用户提供的 Figma 设计稿，完成运动模块正式页面 UI 开发，并与现有运动状态、地图能力、交互链路稳定接通。

### 设计输入

- 设计来源：用户提供的 Figma Make 链接
- 当前约束：先完成模块计划与实施规格确认，再进入代码实现
- 实现基线：优先复用现有 `motion` 模块状态管理、地图容器与运动控制能力，不推翻已完成基础链路

### 阶段范围

本阶段聚焦以下内容：

1. 正式运动页面的结构重建
2. Figma 视觉样式在 Flutter 中落地
3. 调试页与正式页解耦
4. 运动中、暂停、结束、异常等状态在正式 UI 中的映射
5. 页面适配与基础可用性校验

本阶段暂不主动扩展：

1. 首页联动
2. 历史记录列表页
3. 分享、成就、排行等外围功能
4. 与当前 Figma 页面无直接关系的额外视觉扩展

### 阶段实施原则

1. 不直接在当前调试页上堆正式 UI，优先新建正式页面结构。
2. 先做页面骨架与组件拆分，再逐步接入业务状态，避免视觉与逻辑混杂。
3. 尽量复用现有 `Riverpod` 状态和原生地图能力，减少对已完成链路的扰动。
4. 如果 Figma 中存在无法从当前链接稳定提取的细节，先在实施规格中记录待确认项，再和用户确认。

### 阶段建议步骤

1. 读取并拆解 Figma 页面结构、状态和视觉层级
2. 确认正式页面信息架构与组件边界
3. 在 Flutter 中搭建正式页面骨架与样式基线
4. 接入地图区、操作区、统计区和状态展示区
5. 补齐不同运动状态下的 UI 切换
6. 处理适配、异常态和验收收尾

### 阶段里程碑

#### 里程碑 4：像设计稿

- 页面主结构与 Figma 对齐
- 主要视觉样式完成落地
- 地图与浮层叠放关系正确

#### 里程碑 5：像正式产品

- 正式 UI 接通真实运动状态
- 调试页与正式页分离
- 主要交互态和异常态可用
